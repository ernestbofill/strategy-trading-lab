# Decisions

Decisions that outlive a PR, and why. One dated line each, newest first, with the PR number. The PR has the detail.

- 2026-10-25 · The launch path: Milestone 1 (core loop), Milestone 2 (ready to publish), a quiet launch, then the public beta, as in ROADMAP.md. *Your AI's top picks* comes into the launch if there's time; the rest of the launch scope is still open. (#58)
- 2026-10-25 · Template pages are public, and sign-up has "Skip for now, look around": a guest goes through the new-strategy flow (draft in the browser) and signs up to start it. (Ernest, #58)
- 2026-10-25 · Claude has an owner account of its own, on dev and production, to test and check every feature; once the invite gate is on, it gets past it with owner invite links, never a bypass in the code. Owner actions go to an audit log, and the *Production* rules in `CLAUDE.md` still apply. (Ernest, #58)
- 2026-10-25 · From the quiet launch, no sign-up without an invite, until Ernest decides to open sign-ups for the public beta. Until the quiet launch the gate stays off: sign-up is open while the app is built. (Ernest, #58)
- 2026-10-25 · The quiet launch is invite only. Ernest's invite links give the vip role; each vip can invite a few people (3 by default) with their own link; those people are users and can't invite. (Ernest, #58)
- 2026-10-25 · Limits: at most 10 running strategies per user and 60 stocks per strategy. (Ernest, #58)
- 2026-10-25 · Emails go through Brevo from the app's own domain before strangers use the app; the domain is still to choose. (Ernest, #58)
- 2026-10-25 · Adding a stock or fund must be automatic and never need a deploy: an asset is a database row, looked up in the price source's search, with its prices fetched at once. An added stock's one-line description is its sector and industry from the source, not AI-written text. (Ernest's requirement, design proposed in #58)
- 2026-10-25 · *The comeback* keeps the POC's behaviour once its milestones are used (no more steps); the Holding row says so. (Ernest, #58)
- 2026-10-25 · A strategy's first daily check treats each stock as just added: it evaluates the latest finished day, with no backlog of past signals. (Ernest took the recommendation, #58)
- 2026-10-25 · Catalan: Claude translates, Ernest (fluent in both) reviews and corrects; no other reviewer. (Ernest, #58)

- 2026-10-24 · Advanced settings are data: each template lists the params the user may tune, with the screen's range and step (`Template.Settings`), and their words live in the template texts. The API refuses any other key or a value off the screen's steps, then checks the merged params as before; a strategy stores its full params. The params' own ranges stay wider, as what the engine accepts. The zone may start at up to 39% (the spec's "end − 1"), so `DipParams.ZoneStartPct` now accepts up to 39. (#55)

- 2026-10-24 · `CLAUDE.md` is the single source of the instructions for every AI tool (Claude Code is the default). `frontend/CLAUDE.md` and `backend/CLAUDE.md` hold the area rules; Copilot (`.github/copilot-instructions.md`, `.github/instructions/`), Codex and Antigravity (both `AGENTS.md`) are short pointers plus their own specifics, so a rule is changed in one place. (Ernest: "Claude is the default")
- 2026-10-24 · Notification emails: a live signal alert goes out right after the daily check that created it, and the daily overview at 07:00 in the user's time zone (checked hourly); each once (a `notifications` row is claimed before sending, so a crash between claim and send loses that email rather than sending it twice), only to verified addresses, and the overview only to users with a running strategy. The admin setting `EMAILS_ENABLED` is the master switch; the account page has the overview switch, a strategy's own alerts switch comes with the strategy actions. The scoreboard shows signals so far until results exist. (#46)
- 2026-10-23 · The daily check never rewrites the past: a day already evaluated gets no new signal if a setting, the budget or the price history changes later (no back-dated signals or trades); a stock added to a running strategy is evaluated from the day it was added; and a signal is only made while its step still fits in the budget (the budget counts every signal's step amount). Recommended by the review of #45; say if you want it otherwise. (#45)
- 2026-10-23 · The daily check runs right after each price refresh and evaluates up to the last finished US session (16:30 New York, weekdays; a holiday simply has no bar). A strategy starts fresh on its start day, like the POC's backtest. A signal's window is open while the buy conditions hold; a live signal still waiting when it closes is `missed`. A simulation signal is confirmed when created. Each signal's trade is made at the next trading day's open, with the tested fee (0.2% + 1) and the day's rate. (#45)
- 2026-10-23 · The engine is pure code over price bars (no database) and is checked against the POC: golden files hold the POC's status, step and signal days on real prices, and a test must match them every day. The rules' own position is the POC backtest's: a signal on day D is bought at D+1's open whatever the user does, so a buy window gives one step, the cooldown counts from that fill, and a window that stays open gives no second step. (#43)
- 2026-10-23 · Loop development is autonomous: Claude does the whole cycle per item and merges its own PRs (high-risk and docs-only ones too) once reviewed and CI is green, and stops only for a decision that is Ernest's. A PR waiting on one stays open; the rest are merged. A tool refusal is reported, with the permission rule to add, never worked around. (Ernest: "I don't need to approve every merge"; "autonomous unless there's a decision I must make", #41)
- 2026-10-23 · Prices come from Yahoo's chart endpoint directly, as the POC's yfinance does (Ernest: "Yahoo it is"), adjusted for splits and dividends, one refresh a day and a minute after each start, on a schedule set on the admin page (time zone and time, default 22:30 Madrid, after the US close; Ernest's request, like the POC's settings), with "Refresh now" and "Test Yahoo" buttons. The endpoint is unofficial: a failure is logged and shown on `/admin/prices`, and the stored prices stay. Exchange rates are the euro against each currency, from the same source. (#38)
- 2026-10-23 · The frontend's in-browser mock backend is removed (Ernest's call): the real API is the only backend, so the screens and the API can't drift apart. Cloud sessions without database variables can't run the screens; they rely on tests. (#40)
- 2026-10-23 · The user picks a currency (euro, US dollar or British pound; euro by default) at sign-up and in the account. It is the currency of the strategies started afterwards and each strategy keeps its own, so changing it never converts a running one. The tested defaults and backtests stay in euro. (Ernest's request, #35)
- 2026-10-23 · CI runs every backend test, the `[NeonFact]` ones included, against a throwaway PostgreSQL 16 and RustFS (MinIO no longer publishes community images) with `migrations.sql` applied, so no one has to run them by hand before a merge. A `DATABASE_URL` keeps requiring SSL unless it says `sslmode=disable`. (Ernest: "we can't depend on my manual test")
- 2026-10-23 · The admin page switches the API between the dev and production databases, but both URLs are set only in the server's environment (`api.env`: `DATABASE_URL` and `DATABASE_URL_DEV`), never on the page (Ernest's call, option B): knowing the page's password can't point the API at another database. `api.env` is sent with `deploy/backend/deploy-env.ps1` from a gitignored local file. The choice is kept in the service's state directory; a switch is tested first (it answers, no pending migration) and refused on the server while the admin password is the default. A DEV tag in the top bar shows the dev database is in use. (#30)
- 2026-10-21 · The log-in lock (5 tries in 15 minutes, each counted before its password is checked; a good log-in clears it) is counted in memory for every email typed, not on the user row, so it behaves the same for emails without an account and never reveals which have one. A restart forgets it. Account emails go through a background queue so answers never wait on, or reveal, a send. Links use the configured `PublicUrl`, never the request's Host. (#28)
- 2026-10-21 · Accounts as designed in #25, all recommended answers: no email verification before use (only before going live), sign-up never reveals a taken email, log-in by email only, passwords of 10+ characters, 5 wrong tries lock an email for 15 minutes, 30-day sessions (90 at most), template endpoints public. Until accounts have an admin role the page has a fixed password, `STL` (Ernest's call); secrets are write-only, set only on the page (never from api.env), and sealed with the mail account, server and port they were saved with, so changing those can't send them elsewhere.
